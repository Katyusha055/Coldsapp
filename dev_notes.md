## Objective
This document captures the main technical decisions observed in the project and records architecture, data, testing, and security trade-offs for future implementation work.

## 1) Why it would have been better to write directly to the database instead of relying on `POST /clients` during testing
In `backend/clients/tests/service_test.py`, multiple test scenarios prepare data by calling HTTP endpoints (`api_client.post("/clients/")`) and then validate database state. That is valid for end-to-end coverage, but for service/repository testing it mixes two responsibilities:

- fixture creation;
- API behavior validation.

For service and repository tests, direct DB inserts (or repository-level fixture helpers) are more deterministic and easier to debug. Benefits:

- lower coupling across tests (if `POST` breaks, unrelated `GET/PATCH` checks should not fail by dependency);
- faster execution (less HTTP overhead and serialization);
- better fault isolation (a failing layer is easier to identify).


## 2) Why the architecture is feature-based instead of module-type-based
The current structure groups responsibilities by business feature (`backend/clients/` contains `router.py`, `service.py`, `repository.py`, `models.py`, `schema.py`, and tests). This feature-first approach improves:

- local domain cohesion (all client-related logic lives together);
- development flow when evolving a use case (fewer cross-directory jumps);
- scalability when adding new domains (`orders`, `tickets`, etc.) with the same vertical pattern.

Compared with a type-based layout (all routers together, all repositories together), feature-based organization reduces cognitive load and makes ownership boundaries clearer.

## 3) Discovery: `user_id` must not come from the frontend
The implementation already points in the correct direction: `CreateClient` does not expose `user_id`, and the create endpoint injects `user_id` on the backend from authentication context (`get_user_id()`).

This is an important security rule:

- the frontend must not declare data ownership identity;
- backend identity must be derived from token/session;
- row filtering (`WHERE user_id = ...`) must always use authenticated context.

Phase 1 rule: frontend sends token; backend resolves identity.

## 4) Discovery: to organize clients by user, use a foreign key instead of creating one table per user
The current schema correctly uses a single `clients` table with `user_id` as a foreign key to `users(id)`, including `ON DELETE CASCADE`.

Technical reasons:

- avoids table proliferation and operational complexity;
- keeps query planning/indexing stable;
- enforces referential integrity at the database level;
- supports future scaling patterns (row-level controls, partitioning, etc.).

Creating one table per user would increase migration, observability, backup, and maintenance complexity.

# Architectural decisions — modules and system design

## Tickets module

### Soft delete vs. hard delete on tickets
**Decision:** Tickets use a `deleted_at` timestamp instead of physical deletion. This preserves historical records for future analytics (e.g., volume trends, cancellation rates) and prevents accidental data loss from UI mistakes.
**Trade-offs accepted:** Queries must always include `WHERE deleted_at IS NULL`, which adds a filter requirement to every read path. No automatic cleanup is implemented yet — a data retention policy (e.g., purge records with `deleted_at` older than 30 days) is deferred until scale makes it necessary.
**Future ideas:** Scheduled cleanup job once storage or query performance becomes a concern at scale.

### Hard delete on clients
**Decision:** Clients use hard delete. A deleted client record represents a data entry error or duplicate — it carries no analytical value and soft-deleting it would add noise to every query.
**Trade-offs accepted:** If a client is deleted by mistake, recovery requires a backup restore. Acceptable risk given the onboarding is operator-assisted in phases 0–1.
**Future ideas:** Consider a short-window undo mechanism if self-service onboarding is introduced in phase 2.

### `VALID_TRANSITIONS` as a dictionary
**Decision:** Allowed ticket status transitions are encoded as a `dict[str, list[str]]` (e.g., `{"pending": ["in_progress"], "in_progress": ["ready", "cancelled"]}`) rather than a chain of `if/elif` blocks. This makes the transition graph explicit and inspectable, and extending it requires only a dict update.
**Trade-offs accepted:** No enforcement that all states appear as keys; callers assume completeness. Acceptable given the state space is small and defined in one place.
**Future ideas:** If transition logic needs side effects (notifications, audit logs), move to a state machine library. For the current scope the dict is sufficient.

### `ready_at` and `delivered_at` as separate timestamps
**Decision:** Ticket status milestones are stored as discrete nullable timestamps (`ready_at`, `delivered_at`) rather than relying solely on `updated_at`. This allows direct computation of repair duration and detection of equipment left uncollected after the shop notified the customer.
**Trade-offs accepted:** Each timestamp must be set explicitly by the service layer on the correct transition; there is no automatic assignment. A missed assignment silently leaves the field null rather than failing loudly.
**Future ideas:** When a full audit trail is needed, migrate to a `ticket_status_history` table. For MVP, individual timestamps are sufficient.

### `update_ticket` and `update_ticket_status` as separate operations
**Decision:** Editing ticket metadata (description, device info) and advancing ticket status are two distinct service methods with separate validation paths. Status transitions enforce `VALID_TRANSITIONS` and set timestamps; metadata updates do not.
**Trade-offs accepted:** Callers cannot change description and status in a single request. This is an intentional constraint — conflating the two would require merging incompatible validation rules.
**Future ideas:** No change anticipated. The separation reflects a genuine domain distinction.

### `CHECK` constraint on status instead of PostgreSQL `ENUM`
**Decision:** The `status` column uses a `CHECK (status IN (...))` constraint rather than a native PostgreSQL `ENUM` type. Adding or removing a valid status requires only an `ALTER TABLE` statement, not dropping and recreating an enum type.
**Trade-offs accepted:** The valid values are not declared in the type system — they live in the schema SQL and must be kept in sync with `VALID_TRANSITIONS` in code. A mismatch is a silent inconsistency, not a compile error.
**Future ideas:** No change planned. The flexibility outweighs the type-system benefit for this scale.

### Deferred: `job_status_history` table
**Decision:** No history table for status transitions exists yet. The individual timestamps (`ready_at`, `delivered_at`, etc.) cover the analytics use cases of the MVP without the overhead of an append-only history table.
**Trade-offs accepted:** Transition order and intermediate states are not fully reconstructable. Acceptable until a concrete audit or analytics requirement appears.
**Future ideas:** Add `job_status_history (ticket_id, from_status, to_status, changed_at)` when audit requirements or a BI module make it necessary.

### Deferred: `price`, `cost`, and `technician_id` fields
**Decision:** No pricing or technician assignment fields in the current schema. `price` is ambiguous without a billing context (parts cost? labor? total?); `technician_id` adds no value for shops with 1–2 people.
**Trade-offs accepted:** The schema cannot support invoicing or workload tracking. Both are explicit deferrals, not oversights.
**Future ideas:** Add `price` when a customer requests it with a clear billing workflow defined. Add `technician_id` when onboarding a shop with 5+ technicians.

## Auth module

### `PyJWT` + `pwdlib` instead of `python-jose` + `passlib`
**Decision:** `passlib` is effectively unmaintained; `pwdlib` is its designated successor. `python-jose` has known CVEs and no active maintainer. Using `PyJWT` + `pwdlib` selects actively maintained libraries for the two most security-sensitive operations in the stack.
**Trade-offs accepted:** `pwdlib` is less documented than `passlib` — the API is similar but not identical. Migration cost was low at this stage; it would be higher in an established codebase.
**Future ideas:** No change planned. Revisit if `pwdlib` itself stalls.

### `PasswordHash.recommended()` for algorithm selection
**Decision:** Algorithm selection is delegated to `pwdlib` via `PasswordHash.recommended()` rather than hardcoding `bcrypt` or `argon2`. The library adopts updated defaults as the field evolves; the application code does not need to change.
**Trade-offs accepted:** The actual algorithm in use is not visible at the call site. A developer unfamiliar with `pwdlib` must check the library docs to know what is running.
**Future ideas:** No change needed unless the project requires a specific algorithm for compliance reasons.

### `decode_token` separated from `get_current_user`
**Decision:** `decode_token(token: str) -> dict` is a pure JWT utility; `get_current_user` is a FastAPI dependency that wraps it and raises `HTTPException` on failure. Keeping them separate allows `decode_token` to be tested in isolation and reused in non-HTTP contexts (e.g., WebSocket auth, background jobs).
**Trade-offs accepted:** Two functions where one might seem sufficient. The split is intentional and the boundary is clear.
**Future ideas:** No change planned.

### `get_current_user` placed in `utils.py`
**Decision:** `get_current_user` lives in `auth/utils.py`, not in `auth/service.py`. It is infrastructure — it validates a token and resolves an identity — not business logic. Placing it in `service.py` would blur the boundary between domain logic and framework wiring.
**Trade-offs accepted:** A reader unfamiliar with this convention may expect it in `service.py`. The placement is deliberate; a comment in `service.py` can point there if confusion arises.
**Future ideas:** No change planned.

### `CurrentUser = Annotated[dict, Depends(get_current_user)]`
**Decision:** The FastAPI dependency type alias is defined once in `auth/utils.py` and imported by all routers. This ensures a single definition point — if the dependency signature changes, only one file needs updating.
**Trade-offs accepted:** All routers import from `auth/utils.py`, creating a coupling to the auth module. This is expected and acceptable for an auth dependency.
**Future ideas:** If the project grows to support multiple auth schemes, this alias is the correct place to introduce the abstraction.

### `DUMMY_HASH` to prevent timing attacks
**Decision:** When a login attempt uses a phone number that does not exist, the code still runs a password hash comparison against a precomputed dummy hash. Without this, an attacker can distinguish "phone not registered" from "wrong password" by measuring response time, leaking user enumeration data.
**Trade-offs accepted:** Slightly more complex login path. The security benefit is concrete and the cost is negligible.
**Future ideas:** No change planned. Rate limiting (planned post phase 1) adds a complementary layer.

### `ACCESS_TOKEN_EXPIRE_HOURS` configurable via `.env`
**Decision:** JWT expiration is set via an environment variable defaulting to 8 hours, aligned with a typical shop workday. Changing it requires no code deployment — only an environment variable update.
**Trade-offs accepted:** If the variable is misconfigured (e.g., set to 0 or a very large value), all sessions are affected immediately. Acceptable given the deployment is operator-controlled.
**Future ideas:** No change planned. Refresh tokens (post phase 1) will make this less critical.

### `get_user_credentials` separated from `get_user_by_phone`
**Decision:** The repository exposes two distinct queries: `get_user_by_phone` returns public user fields; `get_user_credentials` returns the password hash and is called only during login. This limits how often the hash travels through the application stack.
**Trade-offs accepted:** Two queries instead of one for login flow. The additional round-trip cost is negligible; the principle-of-least-privilege benefit is concrete.
**Future ideas:** No change planned.

### `UNIQUE` constraint on `phone` at DB level
**Decision:** Phone uniqueness is enforced by a database constraint, not only by application-level checks. This prevents duplicate registrations regardless of race conditions or code bugs.
**Trade-offs accepted:** Duplicate registration attempts surface as `IntegrityError` from psycopg, which must be caught and translated to a `409 Conflict` response in the service layer.
**Future ideas:** No change planned.

### `override=False` in `load_dotenv`
**Decision:** `load_dotenv(override=False)` ensures that environment variables injected by Docker or Railway at runtime take precedence over the `.env` file checked into the repo. Without this, a stale `.env` in the image could silently override production secrets.
**Trade-offs accepted:** Local development requires explicit `.env` management — if a variable exists in the shell environment it will not be overridden by `.env`. This is the correct behavior.
**Future ideas:** No change planned.

### Phone as primary user identifier
**Decision:** Users are identified by phone number, not email. In Latin American repair shop contexts, phone is the de-facto business identifier — customers are stored by phone, WhatsApp communication is phone-based, and operators are familiar with phone as a lookup key.
**Trade-offs accepted:** Phone numbers can change; email is more stable as a long-term identifier. Acceptable for phase 0–1 given the onboarding is assisted and the user base is small.
**Future ideas:** Add email as an optional secondary identifier if self-service onboarding requires password recovery.

### Deferred: refresh tokens
**Decision:** No refresh token mechanism exists in phase 0–1. A single JWT with configurable expiration covers the MVP session model. Refresh tokens add storage, revocation, and rotation complexity that is not justified at this stage.
**Trade-offs accepted:** Sessions expire and require re-login. For an 8-hour workday token this is acceptable.
**Future ideas:** Implement post phase 1 alongside rate limiting and the full auth hardening pass.

### Deferred: phone verification and RBAC
**Decision:** No OTP/SMS verification and no role-based access control in phase 0–1. Onboarding is operator-assisted (Steffano), so verification is implicit. All users of the same shop have equivalent permissions.
**Trade-offs accepted:** No self-service onboarding possible; a malicious operator could register fake users. Acceptable risk for the current scale and deployment model.
**Future ideas:** Phone verification via WhatsApp (Evolution API) when self-service onboarding ships. RBAC (owner vs. technician roles) evaluated for phase 2 based on actual customer requests.

### Deferred: rate limiting
**Decision:** No rate limiting on `/auth/token` or any other endpoint in phase 0–1. Documented as an accepted risk; the attack surface is low with assisted onboarding and a small user base.
**Trade-offs accepted:** Brute-force attacks on the login endpoint are currently unrestricted. Mitigated partially by `DUMMY_HASH` (no user enumeration) but not by throttling.
**Future ideas:** Implement as part of the post-phase-1 OWASP Top 10 audit. Candidates: `slowapi` (token bucket per IP) or Railway's edge-level rate limiting.

## General architecture

### Router → service → repository layering
**Decision:** SQL lives exclusively in `repository.py`, business logic in `service.py`, and HTTP concerns in `router.py`. This enforces a unidirectional dependency chain and makes each layer independently testable.
**Trade-offs accepted:** Simple CRUD operations require three files. The overhead is intentional — it keeps the layers from bleeding into each other as the codebase grows.
**Future ideas:** No change planned.

### `row_to_dict` helper per repository
**Decision:** Each repository module includes a `row_to_dict` function that converts psycopg row objects to plain Python dicts. This avoids coupling the service layer to psycopg cursor types and keeps the data contract explicit.
**Trade-offs accepted:** A small amount of boilerplate per module. No shared base class or ORM magic — intentional for transparency.
**Future ideas:** If row mapping becomes complex (nested objects, type coercions), consider a thin dataclass layer. For the current schema, dicts are sufficient.

### Multi-tenant isolation via `user_id` in all queries
**Decision:** Every repository query that reads or mutates data includes `AND user_id = :user_id`. The service never differentiates between "record does not exist" and "record belongs to another user" — both return 404. This prevents cross-tenant data leakage and avoids information disclosure via error messages.
**Trade-offs accepted:** Ownership checks happen implicitly in SQL rather than explicitly in service logic. A developer adding a new query must remember to include the `user_id` filter — there is no framework enforcement.
**Future ideas:** A linting rule or base repository pattern that asserts `user_id` presence could be added if the query count grows large enough to make manual review error-prone.

### `lifespan` event for DB initialization
**Decision:** Database connection setup runs in FastAPI's `lifespan` context manager, not at module import time. This prevents connection errors from surfacing during test collection or import-only operations.
**Trade-offs accepted:** Initialization failures surface at startup, not at import. This is the correct behavior — silent import-time failures are harder to diagnose.
**Future ideas:** No change planned.

### Testing strategy
**Decision:** Service-layer tests run against a real PostgreSQL database rather than mocks. This covers the full `service → repository → DB` chain and catches issues that mock-based tests miss (constraint violations, query correctness, transaction behavior). Mutation testing with `mutmut` runs at 93.6% — the remaining 6.4% is a conscious decision, not an oversight.
**Trade-offs accepted:** Tests require a running database and are slower than unit tests with mocks. Test fixtures use a factory pattern (`create_user`, `auth_headers` in `conftest.py`) to keep setup readable.
**Future ideas:** No change to the real-DB philosophy. If test suite duration becomes a bottleneck, parallelize with `pytest-xdist` before considering mocks.
