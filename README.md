# Coldsapp Clients API

## Overview
This repository exposes a FastAPI backend focused on client management for a repair-shop workflow. The current public API surface is the `clients` module and all routes are grouped under the `/clients` prefix.

The implementation follows a layered structure:
- **Router layer** (`backend/clients/router.py`): HTTP routes, request/response models, path params.
- **Service layer** (`backend/clients/service.py`): orchestration and DB connection lifecycle.
- **Repository layer** (`backend/clients/repository.py`): SQL operations and persistence contracts.
- **Schema/model layer** (`backend/clients/models.py`): Pydantic request/response contracts.

## Runtime and Router Composition
- App entrypoint: `backend/main.py`.
- API aggregator: `backend/api/routers.py`.
- Clients router registration: `/clients` with `clients` tag.

## Authentication Mock
There is no token/JWT/session mechanism yet.

Current behavior:
- The function `get_user_id()` in `backend/core/auth.py` always returns `1`.
- All client endpoints implicitly execute operations as `user_id=1`.
- Multi-user behavior is therefore mocked and constrained to records owned by that fixed user id.

Operational implications:
- Tests seed a user with `id=1` to align with this mock.
- Any request is effectively authorized as the same user.
- A real auth integration will need to replace `get_user_id()` and propagate the authenticated principal.

## Data Model (Clients)
Based on SQL table creation and API response serialization, a client contains:
- `id` (integer, generated by DB).
- `user_id` (integer FK to `users.id`, not exposed in API responses).
- `name` (string, required in DB and Create payload).
- `phone` (string, required in DB and Create payload).
- `description` (string nullable).
- `created_at` (timestamp with timezone in DB, returned as string in API model).

Relevant DB constraints:
- Foreign key `clients.user_id -> users.id` with `ON DELETE CASCADE`.
- Index on `clients.phone` (`clients_phone_index`).

## Request/Response Contracts

### `CreateClient`
Used by `POST /clients/`.

```json
{
  "name": "string",
  "phone": "string",
  "description": "string | null"
}
```

Validation characteristics:
- `name` is required.
- `phone` is required.
- `description` is optional.
- Field-level format/length constraints are not yet defined.

### `UpdateClient`
Used by `PATCH /clients/{client_id}`.

```json
{
  "name": "string | null",
  "phone": "string | null",
  "description": "string | null"
}
```

Validation characteristics:
- All fields optional.
- Unknown fields are rejected by FastAPI/Pydantic validation.
- Repository raises `ValueError("No valid fields provided for update")` if payload has no valid updatable fields after filtering.

### `ResponseClient`
Returned by read/write endpoints (except delete).

```json
{
  "id": 1,
  "name": "string",
  "phone": "string",
  "created_at": "string",
  "description": "string | null"
}
```

Notes:
- `created_at` is serialized as a string from DB timestamp.
- `user_id` is intentionally not included in API response model.

## Endpoints

### 1) List clients
- **Method/Path:** `GET /clients/`
- **Auth behavior:** uses mocked `user_id=1`.
- **Response:** `200 OK` with `list[ResponseClient]`.
- **Scope:** returns all clients owned by current mocked user.

### 2) Create client
- **Method/Path:** `POST /clients/`
- **Body:** `CreateClient`.
- **Auth behavior:** server injects `user_id` from auth mock.
- **Response:** `200 OK` (or `201` acceptable in tests) with `ResponseClient`.
- **Failure modes:**
  - `422 Unprocessable Entity` for missing required fields or wrong types.

### 3) Update client
- **Method/Path:** `PATCH /clients/{client_id}`
- **Path param:** `client_id: int`.
- **Body:** `UpdateClient`.
- **Response:** `200 OK` with `ResponseClient` when row exists.
- **Failure modes:**
  - `422 Unprocessable Entity` when payload types are invalid.
  - `422 Unprocessable Entity` when `client_id` is not an integer.
  - Potential unhandled service/repository exception when no valid updatable fields are provided.
  - `404 Not found` when the client could not be found.

### 4) Delete client
- **Method/Path:** `DELETE /clients/{client_id}`
- **Path param:** `client_id: int`.
- **Response contract:**

```json
{
  "deleted": true,
  "id": 10
}
```

- `deleted` is `false` when target row does not exist for current user.

### 5) Get client by id
- **Method/Path:** `GET /clients/{client_id}`
- **Path param:** `client_id: int`.
- **Response:** `200 OK` with `ResponseClient` when found.
- **Failure modes:**
  - `422 Unprocessable Entity` if `client_id` is not integer.
  - `404 Not found` when the client could not be found.

### 6) Get client by phone
- **Method/Path:** `GET /clients/by-phone/{phone}`
- **Path param:** `phone: str`.
- **Response:** `200 OK` with `ResponseClient` when found.
- **Failure modes:**
  - `404 Not found` when the client could not be found.

## Validation Matrix

### Request-level validation (FastAPI/Pydantic)
- Missing `phone` on create -> `422`.
- Non-integer `client_id` in routes requiring integer path param -> `422`.
- Invalid type in PATCH payload (e.g., `phone` as array) -> `422`.

### Repository-level validation
- PATCH with no valid updatable fields after filtering raises `ValueError`.
- CRUD queries always scoped by `user_id` for ownership isolation.

### THE PROBLEM

So this project is born because of one specific problem i have seen in Latin America: repairing shops and technicians 
usually don't have an automatic system to manage whatsapp and clients, and since they tend to have many clients with 
pending jobs and all communicate through whatsapp, it gets messy really quickly. 

This app is meant to solve that problem by giving an easy-to-use interface and a efficient system to handle the bussiness-client 
relationship.

### The structure

For now it will be divided in two main parts:

-An API built in Fastapi to handle all the backend 
-A Frontend built in JavaScript and another framework yet to be decided to consume that API (spoiler: it will probably be vue.js)
